## 先明确三个结论

1. **可以拿到问答与检索模板，不需要靠反复问参考产品来猜。** 核心都在公开的 [prompts/templates.py](https://github.com/yolo-hyl/medical-rag/blob/4ec5871ad874344d228b19aeed7ab38c4ba0b940/src/MedicalRag/prompts/templates.py)。
2. **没有看到截图所示的专用排版指令。** 基础问答主要约束依据资料、简洁和避免编造，未规定按城市分组、每家写优势、加粗医院名称或展示引用链接。不能保证照抄后就得到截图中的完整风格；截图部署是否增加过其他提示词，公开仓库不足以确认。
3. **仓库不只有本地知识库能力。** [SearchGraph.py](https://github.com/yolo-hyl/medical-rag/blob/4ec5871ad874344d228b19aeed7ab38c4ba0b940/src/MedicalRag/agent/SearchGraph.py)按配置决定是否在本地检索后进入网络搜索；[TencentSearch.py](https://github.com/yolo-hyl/medical-rag/blob/4ec5871ad874344d228b19aeed7ab38c4ba0b940/src/MedicalRag/agent/tools/TencentSearch.py)调用腾讯SearchPro。[默认配置](https://github.com/yolo-hyl/medical-rag/blob/4ec5871ad874344d228b19aeed7ab38c4ba0b940/src/MedicalRag/config/app_config.yaml)将network_search_enabled设为True，但实际部署仍取决于配置、凭据和路由。界面没显示来源，不足以判断某次回答实际用了哪条通道。

## 14组模板分别解决什么问题

| 注册名 | 用途 | 我们可取的部分 | 应当调整的部分 |
| --- | --- | --- | --- |
| basic_rag | 基于资料生成单轮回答 | 问题与材料分开、事实受材料约束 | 不整段拒答，先回答已有依据部分；补充问题类型排版 |
| dialogue_rag | 多轮问答 | 结合当前问题和历史摘要 | 历史回答不能作为新事实；避免上一轮复诊意图覆盖本轮问题 |
| rewriter | 将追问改写成独立检索问题 | 补齐明确的城市、医院、主题指代 | 保留用户条件，不推测医院、疾病或当前位置 |
| summary | 压缩对话 | 保留关键事实和用户意图，不添加新信息 | 区分用户原话、报告原文和模型解释；标记后续更正 |
| call_db | 调用本地检索工具 | 查询独立、明确，选择检索参数 | 继续执行本项目所有权和公共/私人资料范围限制 |
| web_router | 判断资料是否足够、是否联网 | 按具体缺口生成查询，保留已有相关资料 | 判断解析失败不能默认视为资料完整；动态服务不能只凭旧库回答 |
| call_web | 触发搜索工具 | 将查询交给工具 | 继续读取正文；候选摘要不直接成为最终事实 |
| judge_rag | 检查回答是否脱离材料 | 生成后核对事实 | Y/N过于粗略；应指出错配、漏答、无依据项及下一步 |
| ask_user | 决定是否追问，生成1—3个问题 | 只问影响回答的关键缺口，避免引导诊断 | 医院查询一般最多追问一个；用户已提供城市时不重复问 |
| extract_user_info | 抽取已明确的用户事实 | 不推测未出现的信息 | 不自动写入确认档案，不将私人信息发送给公共搜索 |
| handle_query | 单次改写或最多3个子查询 | 多个独立问题分别检索再汇总 | 不照搬由症状主动猜测鉴别诊断的例子；优先按用户所问拆分 |
| update_background | 更新用户纠正/补充的背景 | 新的明确更正覆盖旧信息 | 对话状态更新与档案保存分离，保存仍需既有核对流程 |
| medical_qa_annotation | 给问答标科室与类别 | 数据导入时做检索标签 | 这是离线标注模板，不是患者回答格式 |
| simple_qa | 最简单的问答包装 | 可用于基线比较 | 缺少证据边界和上下文策略，不适合直接替换生产模板 |

## 源码里的实际调用关系

基础回答和子答案汇总均使用basic_rag；多轮RAG类使用dialogue_rag、rewriter和summary。MedicalAgent负责背景抽取、追问和拆分子查询。SearchGraph先本地检索，按配置与缺口判断决定是否搜索，再生成并可检查事实。

需要特别保留我们的改进：SearchGraph的事实检查失败后重试回到生成节点，不等于重新搜索；格式化资料最多取6份，也不是要求答案列6家医院。不能把这些实现细节误当成其广覆盖能力或截图数量的保证。

## 适配给本项目的提示词与运行接入

以下是结合我们的需求重新编写的设计说明，不是参考仓库原文。适合在线问答的阶段已经接入，实际提示词和结构化契约见 `apps/api/app/followup/rag_pipeline.py`，医院排版见 `hospital_templates.py`，共享上下文规则见 `context_policy.py`。具体范围和验证见 [接入记录](接入记录.md)。

### 1. 上下文查询改写

```text
任务：将本轮问题转成独立的公共检索需求，不回答问题。
仅使用当前问题和最近仍有效的对话条件，补齐明确指代。
保留城市、院区、疾病或科室方向、医院等级、数量和异地限制。
区分“列举医院”“医院总数”“具体医院服务”，不要互相替换。
用户明确更换主题时停止继承旧主题；仅更换城市时保留仍有效的筛选条件。
不得补造位置、医院、疾病、诊断或治疗需求；私人身份信息不进入公共查询。
需要追问的确实缺失字段单独列出，不能重复要求已有信息。

输入：当前问题、可用的公开任务上下文。
输出JSON：intent、regions、institutions、care_topic、department、filters、
          quantity、allow_cross_region、needs_clarification、queries。
queries最多3条，每条独立明确。
```

### 2. 多问题拆分

```text
只按用户实际问到的独立事项拆成最多3个检索子任务。
例如“哪些医院、相关科室、院区位置”可以拆分；每个子任务保留同一地区和筛选条件。
单一问题保持原样，不能为了拆分增加病因、治疗或诊断问题。
检索后合并重复机构；同一机构的旧称或已说明的整合关系不能凑成多家。
```

### 3. 资料充分性与补查

```text
逐项判断本轮请求是否已有可支持的资料。
输出已支持事项、缺失事项、可保留的资料ID、建议查询与建议下一步。
建议下一步只可从以下选择：直接回答、读正文、换页、渲染读取、改写查询、
调用已配置备用搜索、追问关键条件、说明服务故障。
医院名单按本轮地区策略检查覆盖，数量是目标而非编造配额。
健康证体检机构或发热门诊专项名单不能证明医院的疾病专科优势。
接口异常、没有候选、网页不可读、资料不足分别说明，不能混为“查无医院”。
不丢弃已有成功证据，不自动放宽地区和等级，不重复消耗无效重试。
```

### 4. 最终回答与排版

```text
先直接回答当前问题，使用当前选中的答题框架。
医院名单：简短开场，必要时按综合/专科或地区分组，连续编号、加粗名称，
每家只补充有依据的位置或服务方向。
疾病就诊选择：围绕相关科室、有依据的服务特点和有条件的选择考虑组织，
不能把“有该科室”写成“最擅长”，不擅自增加外地医院。
比较：证据足够时用表格；短追问：直接短答，不重新展开完整长模板。
原文未提供的事实省略或明确未核实，部分有依据时先回答部分。
来源是否在界面展示与事实是否有依据是不同问题；保留内部证据关联。
日常报告问答不自动变成复诊清单，只有用户明确要求准备材料时才进入该框架。
```

### 5. 回答核对与改进

```text
将草稿与当前问题、条件、证据逐项对照。
检查：是否答非所问、机构或院区错配、重复机构、无依据评价、超出地域、
把目录条数当总数、遗漏主要问题、数量或格式不符合本轮要求。
输出问题类型、对应句段和建议动作；无问题也明确返回通过。
可以仅修正格式时保留事实；需要新事实时转回补查，不能反复靠生成填空。
重试次数和总预算有上限，修正失败时保留有依据的部分。
```
