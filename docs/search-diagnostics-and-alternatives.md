2026-10-18，博查对“广东省 医院名录”返回45条候选，对“深圳市 医院名单”和“北京大学深圳医院 重点专科 地址”各返回50条。记录在 `apps/api/data/official_batch_02/search-provider-checks.json`。候选数量不等于可引用正文数量，也不代表引擎质量排名。当前只有博查搜索凭据可用，未完成多引擎质量对比。

历史深圳运行 `fe9a6b5d69e146f9a523c2f575700f8b`：50条候选，最终1份来源，6次失败读取、2次浏览器尝试，只进行1轮查询。历史广州运行 `6df65ab5543648488b889eeda774c00d`：三轮49/18/47条候选，最终0份来源，10次失败读取、2次浏览器尝试。可确认瓶颈在候选之后的读取/补查链路；旧日志缺少每页失败分类，不能倒推每页究竟是反爬、超时还是解析失败。

本次补充分步统计：返回候选、相关性剔除、重复候选、直接/浏览器尝试、读取成功/失败、提取片段、适用性剔除片段、有效来源及停止原因。统计进入现有 SQLite stages 和运行结果；读取错误使用固定枚举，不记录患者原文、密钥或原始上游错误。日志重启后可查看，但尚不支持从中恢复节点执行。

### 广州零正文问题复现与修复

随后运行 `ea79f2b1280c4e47ad5a632d442e9fec` 确认三轮均有候选，但8次直接读取和2次浏览器读取全部失败，停止原因为页面预算耗尽。逐页复现：靠前政府旧链接出现403、浏览器404或正文过短，下载型文档站出现403/555；同批候选中有能够读取的广州医院目录，却被这些页面挤到读取预算之外。

地区名单排序现过滤Word/XLS下载或文档查看器落地页，提高城市医院目录的优先级；规则不针对某个城市。读取医院名录时优先抽取“机构名称＋地址”的连续原文范围，保留更名、整合等身份描述，去除医生团队、城市导航及相关推广链接的干扰；没有这种结构的官方名录仍走普通正文节选。答案提示要求合并明确别名/整合关系，不能通过院区或旧称凑医院数量。失败文案不再要求用户重复补充已经给出的城市。

真实检索及模型回答结果保存在 `apps/api/data/official_batch_02/guangzhou-retrieval-check.json`，不将商业目录收录数当作官方医院总数，也不将其等级字段冒充本次行政核验。

## 搜索替代方案

### 广州服务故障追查（2026-10-18）

运行 `8dcdd5b5f25a45c8b3f0bea76d089798` 在博查搜索阶段收到HTTP 403，候选及最终来源均为0，并非正文过滤丢失。运行时只有博查可用，其他适配器的存在不等于已配置可用的备用服务。随后直接复测三个广州检索词，分别返回49、50、48条候选，表明拒绝具有间歇性；仅凭403无法断言是密钥、额度或上游访问策略中的哪一种原因。

现在对POST搜索响应中的403作有限分类：正文明确表示授权或额度错误时不重试；原因不明的拒绝先尝试其他已配置引擎，仍不足时对原通道最多恢复请求一次。同一搜索内不会递归重试，持续失败仍以服务故障结束，不改成“没有医院”；原始上游正文、凭据不写入诊断日志。不使用浏览器绕过搜索API授权。

关闭缓存读取后的完整“广州有哪些医院”实测列出8家，耗时21.8秒，自动事实核对通过；仍有网页读取失败，保留partial状态，不将其标成全链路成功。结果位于 `apps/api/data/official_batch_02/guangzhou-service-recovery-check.json`。自动测试覆盖间歇403恢复、持续403限次、明确授权/额度错误停止，以及优先备用通道。

SearXNG接入：由运维启动可信实例，在其 `settings.yml` 的 `search.formats` 开启 `json`；设置 `SEARXNG_URL=http://127.0.0.1:8088`（示例）、`WEB_SEARCH_PROVIDER=searxng`。按照[官方API](https://docs.searxng.org/dev/search_api.html)请求 `/search?q=...&format=json`。国内模式还要求实际选择国内上游引擎并设置 `SEARXNG_DOMESTIC_ONLY=true`，不将自己部署误当不使用境外上游。实例403、非JSON响应、零结果且有上游引擎故障分别作为故障处理，不当作没有医院。当前Docker daemon未启动，本次未安装或启动SearXNG服务。

参考项目使用的腾讯SearchPro也已独立适配。返回的passage只作候选，继续经过本项目正文读取和来源核对。现有腾讯凭据实测返回 `ResourceNotFound`，按服务不可用处理；默认关闭，未替换博查。安装 `apps/api/requirements-search-tencent.txt`，配置 `TENCENT_SEARCH_ENABLED=true` 和腾讯凭据，确认服务已开通后可设 `WEB_SEARCH_PROVIDER=tencent`。根据[官方SearchPro文档](https://cloud.tencent.com/document/product/1806/121811)，Cnt有套餐限制，默认省略。OCR/ASR开通不等于搜索开通。

自动模式下，失败、零结果或少于 `min(limit,4)` 条候选时尝试其他已配置通道，合并去重并保留已有结果。显式指定provider只调用该通道，便于定位。候选补查阈值不等于最终答案数量；答案仍受正文证据和地区范围限制。

## LangGraph检查点的适用方式

后续已接入本地SQLite持久化阶段检查点、管理员故障诊断和有界恢复，当前使用与边界以[管理员故障定位与检查点恢复](管理员故障定位与检查点恢复.md)为准。以下保留初期方案背景。

[官方持久化文档](https://docs.langchain.com/oss/python/langgraph/persistence)支持线程状态检查点、故障恢复和历史回溯。开发可用SqliteSaver，生产多实例可用PostgresSaver；MemorySaver不能跨进程重启保留状态。本次尚未迁移LangGraph。

建议节点：规划 → 搜索 → 筛选 → 逐页读取 → 覆盖判断 → 改写/备用通道 → 生成 → 回答核对。

thread_id绑定用户和运行；保存候选账本、完成页、证据、失败队列、预算、查询版本和下一节点。网络故障有界重试，权限或服务未开通切通道；HTTP成功但正文为空、名单不足走覆盖分支，不能只依赖异常RetryPolicy。恢复时跳过已成功任务，超期网页重新核验。总预算跨恢复保留；创建档案、保存报告、追加对话等写操作需要幂等，不能因重放重复执行。
