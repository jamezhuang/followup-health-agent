# 医院外部检索流程：开源方案与插件调研

调研日期：2026-10-19。本文是文档与代码方案调研，不代表这些外部服务已完成接入或效果实测。

## 结论

保留现有任务规划、来源分级、证据核验和回答流程，按环节替换或补强工具。当前优先级是第二搜索通道、浏览器排队、按问题缺口补查、证据节选；暂不增加一套多智能体研究框架。

项目已有搜索适配器和 Crawl4AI 隔离读取器。适配器存在不等于服务已配置可用。`apps/api/app/browser_reader.py` 使用单槽信号量且非阻塞获取，忙时返回 `browser_busy`。这属于调度问题，安装另一个提示词 skill 不能直接解决。

## GitHub 上直接相关的故障案例

[SearXNG Discussion #3542](https://github.com/searxng/searxng/discussions/3542) 讨论请求只得到 HTML、无法返回 JSON 的问题。官方 API 文档进一步说明：未启用的输出格式会返回 403，许多公开实例禁用了 JSON。因此应先检验实例的 JSON 配置，不能将这种错误统计成“没有搜到医院”。这也不能用来推断其他搜索供应商的 403 原因。

## 建议工作流

1. 结构化理解原话，得到医院实体、地区、院区、问题列表和缺失条件。医院别名和错别字允许纠正；同名有歧义时保留候选。
2. 优先复用尚有效的已核验官网绑定；未知医院从搜索服务返回的真实 URL 开始发现，不拼接猜测域名。
3. 第一搜索通道未找到可核验官网或所需字段时，触发第二通道。触发依据是有效证据缺口，而非只有候选条数少才补查。
4. 核验医院身份及适用院区。搜索标题只能帮助排序，不能单独授予官方身份。
5. 优先普通 HTTP；必要时进入有界浏览器队列。官网首页没有答案时，沿实际导航链接寻找院区介绍、交通、就诊指南或联系页面。
6. 为每个问题保存字段级证据：来源 URL、原文、发布日期（有则记录）、抓取时间、医院及院区、来源等级、冲突。原文保存在证据记录中，只将相关节选送入生成上下文。
7. 只补查尚缺字段。例如地址已确认但公交未确认，就只搜索交通；“有正文”不代表所有子问题已覆盖。
8. 生成逐点回答并核对每条结论与证据的一致性；缺证据的部分明确说明，避免输出无关资料堆砌。

## 插件与 skill 的定位

插件目录中查到可选 Firecrawl 集成，可用于当前开发研究中的搜索、读取与失败页面诊断；当前并未连接或调用它。连接聊天工具里的插件不等于后端接入，生产系统仍需独立的服务调用、配置、预算及验证。

Firecrawl 官方 CLI 自带 agent skills，Playwright CLI 也提供适合开发工具的能力。skill 主要提供工具使用步骤和策略，不自带搜索索引、服务额度或医院官方身份库。本文没有安装这些 skill，也不将外部仓库的 skill 内容当作项目指令执行。

## 下一轮实验

冻结当前版本作为 A。B 只增加第二搜索通道；C 在 B 上增加浏览器有界排队；D 再增加按字段补查和证据压缩，逐阶段比较，避免一次更换全部组件。

既有六省样本只用于回归；另设开发期间未使用的跨省医院留出集，包含未知医院、同名医院、多院区、更名或官网迁移、动态网页及官网信息确实缺失等情形。测试输入不提供官网 URL；评测参考 URL 与答案只交给评测程序，禁止流入 agent。

记录官网发现率、核验准确率、正文读取成功率、字段覆盖率、答案事实正确率、引用支持率、错误官方归属次数、P50/P95、输入与输出 token、搜索/抓取 API 实际费用及超时率。完整性和真实性分开评分；不使用同一个模型的单一判断作为全部真实性依据。新方案先影子对照，再决定是否替换默认工具。

最终选型需要实际可用的第二通道。无法使用凭据或实例时应报告未实测，不将文档能力当作实验结果。
